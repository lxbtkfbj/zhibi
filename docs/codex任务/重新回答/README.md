# 重新回答：共同约定

这一包改聊天里最新一条回答下面的「重新回答」：改成「退回到那句话之前、把原话原样再发一遍」。这和作者那句话上的「修改」不改字直接发送是同一个效果，走能查资料、翻手册、联网、动手改书的完整路子。只有一个任务，只改前端。

本包的任务都照这一份约定，不照别的目录的 README。

1. 先读本文件，再读任务文件。设计在 `docs/设计说明.md` 9.13「重新回答改成原话重发」。
2. 开工前 `git status` 不干净就停下来问，不要动、也不要替别人提交没提交的改动。
3. 产品代码只改前端 `frontend/src/pages/workspace/` 里的聊天：`Chat.tsx`、`LiveChat.tsx`、`chatModel.ts`，要的话还有 `frontend/src/lib/chat.ts`。后端、提示词、数据库一律不动，没有迁移。界面上的字逐字照任务文件；任务没写到、你自己补的字列进验收说明。
4. 不要升级、重启或改动作者日常的 8000／4320 服务、日常 worker 和书库，不对日常环境运行 `start.ps1`／`stop.ps1`。**不调真实模型**：浏览器测试用独立后端加演示模型。
5. 什么时候自己定，什么时候停下来问：
   - 自己定，做完在完成说明里单独列出来：
     - 测试里写死的旧指纹、旧文字和开工时 HEAD 对不上，而那份文件本任务没动过（和开工时 HEAD 逐字节一致）：改测试跟上 HEAD。
     - 本任务有意改了的东西，旧测试还认旧的：照任务第 5 节的新样子改测试。有意改的包括：重新回答发什么请求、原来那句和旧回答去哪了、「修改」的两处字、回答消息多出来的字段。任务第 5 节点名的那几条浏览器测试都属于这一类，照第 5 节改断言不算「放宽」。
     - 和本任务无关、开工前就坏了的测试：修法是机械的（同第一条），直接修；要改产品代码或者改变行为才能修好的，停下来问。
     - 任务没写到的实现细节：字段和函数叫什么、提醒框怎么拆组件、请求体怎么拼、和 `send` 共用哪几段、单元测试放哪个文件。
   - 停下来问：
     - 要改后端、提示词、数据库，或者要动聊天以外的页面；
     - 要动任务写死的字和行为（比如想给更早的回答也加「重新回答」、想顺手撤销记忆或者改过的书）；
     - 任务的要求和现有代码真的打架，两种做法都说得通，而且会影响作者怎么用；
     - 要删测试、跳过测试，或者放宽和本任务无关的断言才能过；
     - 要动作者日常的服务和书库，或者要调真实模型；
     - git status 不干净（第 2 条）。
6. 检查：开发中只跑相关测试；提交前跑一次全量，全部通过。
   - 前端（`frontend/`）：`npx tsc -b && npm run lint && npm run build && npm run test:workspace`
   - 浏览器测试（独立后端加演示模型）：任务第 5 节要跑的六条，改完重跑，全过。
   - 后端没改，不用跑后端全量；装修、精髓两套页面比对也不用跑（没改公共样子）。
7. 验收写在 `docs/重新回答验收.md`（要写什么见任务第 6 节）。截图三张，放在 `docs/重新回答验收/`，用独立环境截。
8. 直接在当前分支上做，不推送。提交信息以「重新回答：」开头。
9. 做完用一段中文告诉作者：改了哪些文件、检查和浏览器测试的结果、截图在哪、自己补的字；按第 5 条自己定的事单独列出来；告诉作者这次只改了网页，作者那边的网页刷新一下就是新的，不用重启服务。
