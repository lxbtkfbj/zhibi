# 用量记账：共同约定

这一包修调用记录里记的用量：群聊里编辑部边查边答的那几个来回（调工具的来回），记下的输入、输出 token 比实际多出几倍到几十倍。只有一个任务，只改后端记账的几行。

本包的任务都照这一份约定，不照别的目录的 README。

1. 先读本文件，再读任务文件。
2. 开工前 `git status` 不干净就停下来问，不要动、也不要替别人提交没提交的改动。
3. 产品代码只改 `backend/app/llm/router.py` 里记用量的地方（任务第 1 节）。提示词、前端、数据库一律不动，没有迁移。
4. 不要升级、重启或改动作者日常的 8000／4320 服务、日常 worker 和书库，不对日常环境运行 `start.ps1`／`stop.ps1`。**不调真实模型**：测试用假的流式小块。
5. 什么时候自己定，什么时候停下来问：
   - 自己定，做完在完成说明里单独列出来：
     - 测试里写死的旧指纹、旧文字和开工时 HEAD 的提示词或代码对不上，而那份文件本任务没动过（和开工时 HEAD 逐字节一致）：改测试跟上 HEAD，提示词和代码都不动。
     - 和本任务无关、开工前就坏了的测试：修法是机械的（同上一条），直接修；要改产品代码或者改变行为才能修好的，停下来问。
     - 任务没写到的实现细节：怎么记住最后那份用量、要不要抽一个小函数、测试放哪个文件、怎么组织。
   - 停下来问：
     - 要改 `router.py` 以外的产品代码，或者要动提示词、界面、数据库；
     - 想顺手改已经记下的旧记录（任务第 2 节写明不改）；
     - 任务的要求和现有代码真的打架，两种做法都说得通，而且会影响记下来的数；
     - 要放宽断言、删测试或跳过测试才能过；
     - 要动作者日常的服务和书库，或者要调真实模型；
     - git status 不干净（第 2 条）。
6. 检查：开发中只跑相关测试；提交前在 `backend/` 跑一次全量，全部通过：`uv run ruff check . && uv run ruff format --check . && uv run pytest -q`。前端没改，不用跑前端检查和页面比对。
7. 验收写在 `docs/用量记账验收.md`：改了哪几行、新测试在没改的代码上怎么挂的、全量结果。不用截图。
8. 直接在当前分支上做，不推送。提交信息以「用量记账：」开头。
9. 做完用一段中文告诉作者：改了哪些文件、测试和全量检查结果；按第 5 条自己定的事单独列出来；提醒作者升级后要重启服务，新记的数才对。

## 先后（给作者和设计方看的，Codex 不用管）

1. 本目录提交以后，工作区干净就能发 `给Codex的话.md`。和「拆书调提示词」那一包不碰同一个文件（那包不动 `router.py`，测试文件也不重叠），谁先谁后都行；只是别两包同时做，一个提交了再发另一个，不然 Codex 看到工作区不干净会停下来问（第 2 条）。
2. Codex 做完，设计方复核：`git diff` 里产品代码只有 `router.py` 记用量那几行；验收里有新测试在没改的代码上挂掉的那一句；看全量日志。然后重启作者的服务（没有迁移），请作者在《佔位》的群聊里用 gemini-4 问一句要查东西的话，设计方只读看新记的那几条：每个来回的输入应该是请求字数的 0.6～0.8 倍上下（和同一个模型直接写字的记录一样），不再是几倍、几十倍。
