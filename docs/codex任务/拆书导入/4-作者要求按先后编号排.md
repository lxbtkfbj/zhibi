# 小修 3：作者要求按加进来的先后编号排，不靠时钟

## 起因

小修 2 验收时，后端全量里有一项测试在同一套隔离环境里前两轮都失败、第三轮通过（详见 `docs/拆书导入验收.md`「小修 2」最后一节）：

- `tests/test_api.py::test_idle_and_non_reader_notes_are_saved_then_classified[None-queued-None]`
- 预期 `['已有的作者要求', '下一章节奏再快一点']`，实际顺序反了。单项、整个 `test_api.py` 都通过。

设计方查过：作者要求（`author_requirements`）只按 `created_at, id` 排先后，`created_at` 在模型和迁移 0007 里都是数据库的 `clock_timestamp()`；测试先建好「已有的作者要求」并提交，之后才发插话加新要求，代码里也没有地方把旧要求整份重写。时间戳会倒过来，只能是数据库那台机器的时钟往回跳了（Windows 上的 Docker 虚拟机校时偶尔会这样）。不管根因是不是这个，拿墙上时钟排「谁先谁后」本来就不稳：作者那边的要求列表、带给编辑部的要求，顺序也可能偶尔乱。

## 0. 共同约定

照 `2-小修.md` 第 0 节（只照那一节），只有这几处不同：

- 只改后端：模型、一份新迁移、排序的地方、测试。不改前端、不改提示词、不改页面上的字；页面比对两套不用跑，前端全量照跑（确认没碰坏）。
- 验收接在 `docs/拆书导入验收.md` 后面写一节「小修 3」，不用截图。
- 提交信息以「拆书导入：」开头。
- 作者日常库以后用 `启动.cmd` 启动时会先自动备份再升级迁移，这一包不用、也不许碰日常库。

## 1. 要改的

1. 新迁移（接在现有最新的后面）：`author_requirements` 加一列 `seq`，整数、自增、不为空、加索引。已有的行按现在的顺序（同一本书里 `created_at, id`）回填，回填完自增从最大值后面接着走。
2. 所有给作者要求排先后的地方，一律改成按 `seq`：`Book.author_requirements` 的 `order_by`、`services/requirements.py` 的 `list_requirements`，以及全仓库其他按 `AuthorRequirement.created_at` 排要求顺序的地方（先搜一遍，列进验收说明）。`created_at` 留着照旧记时间，只是不再拿来排先后。
3. 要求的文字、来源、范围、去重、墓碑这些规矩都不变；对作者来说顺序本来就是「先加的在前」，这次只是让它不再受时钟影响。

## 2. 测试

1. 迁移：一份有几本书、每本几条要求（`created_at` 各不相同，还有两条 `created_at` 相同的）的库，升级以后每本书按 `seq` 排出来和升级前按 `created_at, id` 排出来一模一样；降级能回去。
2. 时钟往回跳：先加一条要求，再把它的 `created_at` 改到很晚以后（模拟后来时钟回跳），再加第二条，列表里仍然是先加的在前；`Book.requirements` 和 `list_requirements` 都这样。
3. 原来那项 `test_idle_and_non_reader_notes_are_saved_then_classified` 不改，后端全量跑两轮都要全过。
