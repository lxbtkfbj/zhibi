# 预设管理：共同约定

这一包让主编在群聊里每回一句发给模型的字，改由一份「预设」拼出来：预设是一块一块的预设块，能开关、能排先后、能改；系统自带的预设锁着，要改就复制一份；程序的数据用占位符插进块里；每一块都能看来历。两个任务：任务 1 做后台（预设怎么存、怎么拼、怎么检查，主编群聊改用预设，加一本手册），任务 2 做页面。任务 1 提交了再做任务 2。

本包的任务都照这一份约定，不照别的目录的 README。

1. 先读本文件，再读任务文件。设计在 `docs/设计说明.md` 10.7「预设管理」。
2. 开工前 `git status` 不干净就停下来问，不要动、也不要替别人提交没提交的改动。
3. 改哪些：
   - 任务 1：后端。聊天那几处、`router.tool_rounds`、新加的预设代码和接口、迁移 `0031`、`prompts/catalog.py` 里任务写明的那几句说明。`backend/app/presets/` 和新手册 `prompts/skills/standards.md` 从本目录 `git mv` 过去，逐字节一样。别的提示词一个字都不动，前端不动。
   - 任务 2：前端。新页面 `/presets`，加上系统设置、提示词页、调用详情三处入口。后端不动；页面要用的东西接口里没有，停下来问。
4. 不要升级、重启或改动作者日常的 8000／4320 服务、日常 worker 和书库，不对日常环境运行 `start.ps1`／`stop.ps1`，迁移只在测试库和你自己的独立库上跑。**不调真实模型**：要看效果用演示模型。
5. 什么时候自己定，什么时候停下来问：
   - 自己定，做完在完成说明里单独列出来：
     - 测试里写死的旧指纹、旧文字和开工时 HEAD 对不上，而那份文件本任务没动过（和开工时 HEAD 逐字节一样）：改测试跟上 HEAD。
     - 本任务有意改了的东西，旧测试还认旧的：照任务里写的新样子改测试。有意改的包括：主编群聊的系统提示和资料改由预设拼；手册目录多了「写书的标准」；`catalog.py` 那几句说明；系统设置多一张卡；提示词页多一个链接；调用详情多一块「用的预设」。任务里点名的旧测试都属于这一类，照新样子改断言不算「放宽」。
     - 和本任务无关、开工前就坏了的测试：修法是机械的（同第一条），直接修；要改产品代码或者改变行为才能修好的，停下来问。
     - 任务没写到的实现细节：文件放哪、函数叫什么、接口参数和返回的细节、表的列怎么命名、组件怎么拆、拖动用什么写、测试放哪个文件。
   - 停下来问：
     - 要改预设的十九块、新手册，或者任务没点名的提示词；
     - 要动任务写死的东西：只管哪一条路、占位符的名字和值、「什么时候发」的几种和判断法、拼法、检查的几条和拦不拦、作者看到的字；
     - 任务的要求和现有代码真的打架，两种做法都说得通，而且会影响主编收到什么，或者作者怎么用；
     - 要删测试、跳过测试，或者放宽和本任务无关的断言才能过；
     - 要动作者日常的服务和书库，或者要调真实模型；
     - git status 不干净（第 2 条）。
6. 检查：开发中只跑相关测试；提交前跑一次全量，全部通过。
   - 任务 1：`backend` 下后端全量；前端没改，不用跑前端。
   - 任务 2：`frontend` 下 `npx tsc -b && npm run lint && npm run build && npm run test:workspace`；浏览器测试（独立后端加演示模型）跑任务 2 第 5 节的新测试，以及系统设置、提示词页、调用详情相关的旧测试；后端没改，不用跑后端全量。没改公共样子，装修、精髓两套页面比对不用跑。
7. 验收写在 `docs/预设管理验收.md`，任务 1 先写，任务 2 接着写；截图放 `docs/预设管理验收/`。
8. 直接在当前分支上做，不推送。提交信息以「预设管理：」开头，一个任务一次提交。
9. 做完一个任务，用一段中文告诉作者：改了哪些文件、测试结果、验收文档在哪；按第 5 条自己定的事单独列出来。任务 1 还要告诉作者：这次改了后端、有新迁移，要重启服务才用上，设计方复核完会替作者重启。任务 2 告诉作者：网页刷新一下就是新的。
