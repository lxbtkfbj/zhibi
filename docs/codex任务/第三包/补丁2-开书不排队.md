# 补丁 2：开书不排队（只改后端）

> 先读 `docs/codex任务/第三包/README.md`、`3-开书新三步.md`、`6-和编辑部聊天.md`、`补丁1-群聊和开书改进.md`（都已完成并提交）。本补丁只改开书流程和群聊在「挑方向」这一步的处理，**不改前端**：界面由设计方另外重做（包括底部「补齐开书稿」「开写」这些按钮），`frontend/` 下一个文件都不要动。

## 为什么改

作者真模型试用后的两条意见：

1. **聊定的东西落不了地**。作者在「挑故事方向」这一步和编辑部聊了很久，说「你先把这些内容填到设定集里吧」，主编出了方案卡（一条定调、一张主角卡、两条往事与秘密、一条写作要求），作者点〔按这个来〕。结果因为任务正停在「挑故事方向」，整张方案被当成修改意见交给这一步，主编重出了三个故事方向，**设定库一条也没进**。作者要的是：「想让 AI 改哪个，直接说、直接改就行」。
2. **定调、设定、大纲不该排队确认**。现在挑完方向，要先确认「定调和设定」，才出大纲，再确认大纲，才能开写。作者要的是三份稿子随时都能改、谁先谁后都行，不用一关一关点确认。

这个补丁做三件事：

- **挑方向这一步「敞开」**：等作者挑方向时，群聊和方案卡跟空闲时一样，直接落地（改定调、改／建设定、记要求）；只有明确要新方向的话，才重出三个（第 1 节）。
- **「补齐」**：作者可以不挑方向，用已经聊定、写好的定调和设定，让编辑部把剩下的补齐（第 2 节）。
- **挑了方向或补齐以后一口气写完**：定调 → 设定 → 大纲 → 第一个单元的章纲，中间不停；写完书就是「可以开写」，只剩作者点开写这一个决定（第 3 节）。

规则不变：群聊仍然分三种话，拿不准仍按提问闲聊处理；私聊仍然只商量；作者写的、锁住的设定，编辑部不覆盖；开书写完**不自动开写**。

## 1. 挑方向这一步「敞开」

### 1.1 什么叫敞开

`app/services/jobs.py` 加：

```python
def open_wait(job) -> bool:
    """等作者挑故事方向的这一步：聊天和方案卡照空闲时处理。"""
    return (
        job is not None
        and job.status == "waiting_author"
        and job.kind == "book_setup"
        and not is_legacy_setup(job)
        and (job.pending or {}).get("kind") == "setup_pitches"
    )
```

`setup_pitches` 的等待内容（`pitches_gate_node` 里的 `interrupt`）加一项 `"open": True`。已经停在这一步的旧任务没有这一项，照 `open_wait` 判断，不靠这一项。

### 1.2 群聊

- `group_notes.waiting_feedback(job)`：`open_wait(job)` 时返回 `False`（和 `setup_prefill` 一样）。这样等挑方向时，群聊的话走空闲时的路（补丁 1 第 3.1 节：先存、后台判断、`apply_intent`）：改设定就直接改，写作要求就记，提问就答。
- **要新方向的话**照旧重出：`receive_note` 里，在补丁 1 第 2 节的程序判断之后、交给模型判断之前，如果 `open_wait(job)` 并且 `wants_new_pitches(text)`，照旧返回 409 `use_feedback`（前端已经会把这句话交给重出三个故事方向的接口）。
- `wants_new_pitches(text)` 写在 `app/services/chat_context.py`，`wants_plan` 旁边：去掉标点后不超过 200 字，并且含下面之一：`再来三个`、`再出三个`、`重出`、`重新出`、`换三个`、`换一批`、`换几个方向`、`都不要`、`都不满意`、`都不喜欢`。
  - 例：「都不满意，第一个的主角配第二个的金手指」「再来三个，别写穿越」算；「主角不要像云澈那么冲动」「把老怪的设定写进设定库」不算。
- `apply_intent` 里的 `rewrite_target(..., require_idle=True)`：敞开时也要能改。改法见 1.4。

### 1.3 方案卡

`chat_plans.apply_background`：`open_wait(job)` 时**不**交给任务，和空闲时一样逐条 `apply_item`（定调、设定库、大纲、写作要求各按原规则落地，每条都有结果、能撤销）。其他等待（大纲、下一篇、卷纲、章纲）照旧交给任务。

照办完，如果定调或设定库里至少有一条落地成功（`edit` 或 `created`），主编在群聊里接着说一句（只在敞开时）：

```text
照方案办好了。要我按现在的定调和设定把开书稿补齐吗？点底部的「补齐开书稿」就行；想先看看三个故事方向也可以，挑一个，我按那个方向写。
```

### 1.4 敞开时允许改一处

`library_ai.rewrite_target` 里，`require_idle=True` 且 `allow_waiting=False` 时会拦住正在等作者的任务（现在只放过 `setup_prefill`）。改成也放过 `setup_pitches`：

```python
Job.pending["kind"].astext.not_in(["setup_prefill", "setup_pitches"])
```

这样作者在设定库页面上「改这一项」、群聊里说「把主角改成……」，等挑方向时都能直接改。

## 2. 「补齐」：用已有的定调和设定接着写

### 2.1 接口

`PitchDecision.action` 加 `"fill"`：

```python
class PitchDecision(BaseModel):
    action: Literal["pick", "redo", "start", "fill"]
    ...  # 其余字段不变
```

`POST /jobs/{job_id}/pitches`，`action = "fill"`：

1. 必须是等挑方向（`_setup_gate(session, job_id, "setup_pitches")`，同 `pick`）。
2. 书的 `concept.story` 去掉空白后为空：返回 422 `还没有定调。先挑一个故事方向，或者在群聊里聊定了让我照方案办。`
3. `length`（五档之一，可不给）、`title`（可不给）规则同 `pick`，照 `pick` 记作者要求。另记一条作者要求（来源 `answer`）：`开书不挑故事方向，用已经写好的定调和设定补齐。`
4. 作者消息内容：`不挑方向了，用现在的定调和设定补齐开书稿。`
5. 恢复任务：`{"action": "fill", "length": …, "title": …}`。

### 2.2 流程

`pitches_gate_node` 收到 `fill`：

- `pitch = {"from_story": True, "length": 作者选的或推荐的篇幅}`，作者给了书名就加 `"title"`；
- 和 `pick` 一样 `goto="intake"`，`queue = ["concept"]`，并带上第 3 节的 `piece_gates: False`。

`concept_node` 遇到 `pitch.get("from_story")`：

- 读数据库里现在的 `concept.story`（`live_state` 已经读回）；
- 照常调 `draft_story`，只是 `pitch` 这个变量换成：

```text
作者已经定好了定调的一段话，一个字都不要改，照着它补齐其余各项：
{现在的 concept.story}
```

- 拿到结果后，`value["story"]` 一律换回原来那段话（逐字），其余各项（书名、类型、标签、目标读者、基调、底牌等）照常用模型给的；底牌和书名的既有规则不变（作者改过的底牌不覆盖，作者给的书名优先）。

## 3. 挑了方向（或补齐）以后不再停

### 3.1 开关

`SetupState` 加 `piece_gates: bool`。检查点里没有这一项的旧任务按 `True` 处理（照旧一关一关等确认）。

离开挑方向这一步时，`update` 里都带上 `piece_gates: False`：作者 `pick`、作者 `fill`、一口气模式自动挑推荐方向。

### 3.2 不停

`piece_gate_node` 开头：`state.get("piece_gates", True)` 为 `False` 时，每一块（定调、设定库、大纲）都直接 `_confirm_piece`，大纲之后照旧进 `finalize`。和原来作者点「确认」做的事完全一样（包括第 1 卷记成已批准等），只是不等作者。

`_confirm_piece` 里「一步一步看时定调先标成 waiting」那一句（`if piece == "concept" and state.get("mode") != "oneshot"`）在 `piece_gates` 为 `False` 时不生效，定调直接标 `confirmed`。

### 3.3 原来在确认那一关给作者看的东西，不能丢

不停的时候，在 `_confirm_piece` 之前：

1. **提醒**：这一块的 `warnings`（定调的、大纲的；设定库的原来就会存）都存成待处理的建议：`SettingSuggestion(kind="review", title=提醒原文, payload={"op": "note", "why": 提醒原文})`，同一本书已经有同样标题、还没处理的就不再存。
2. **替作者做的决定**：这一块有 `decisions` 时，主编在群聊里发一条：

```text
替你做了这几个决定，想换哪个就在群聊里说：
· {话题}：用了「{选中的}」（也可以：{其他选项，用「、」隔开}）
```

   每个决定一行；没有其他选项的不写括号。没有决定就不发。

### 3.4 写完

`finalize_node` 在 `piece_gates` 为 `False` 时，主编说的话换成：

```text
开书稿齐了：定调、设定 {N} 条、大纲排到第一个单元的章纲。哪里不对，直接在群聊里说，或者在页面上改；满意了点「开写」。
```

`N` 是书里角色卡片和其他设定条目的总数。书的状态照旧改成 `ready`，任务照旧成功结束。**不自动开写**，开写还是走 `POST /books/{id}/write`。

## 4. 开书方式和「先写设定」

- 新书的开书方式还是两种，存的值不变：`puzzle` 改成表示「先给我三个方向挑」，`oneshot` 表示「直接用主编推荐的方向写完」。两种在挑完方向以后都不再停（第 3 节）。
- **「先写设定」不再单独停一步**：新建任务时不管传不传 `prefill`，都直接出三个故事方向（`route_start` 一律走 `pitches`），因为等挑方向时已经能写设定、能照方案办（第 1 节）。已经停在 `setup_prefill` 的旧任务照旧能点「出三个故事方向」。
- 接口里 `prefill` 这个字段先保留（前端还在传），只是不再起作用。

## 5. 兼容

- 已经过了挑方向、正停在「确认定调和设定」或「确认大纲」的任务：检查点里没有 `piece_gates`，照旧等作者确认，确认、提意见都照旧。
- 作者日常库里正停在挑方向的书：升级后这一步就是敞开的，挑方向或补齐以后不再停。
- 第二包和更早的旧任务：照旧只能「按新流程重开」。
- 写作中的各种拍板（下一篇、卷纲、章纲、试读、卡住的章）都不变。

## 6. 给界面的约定（界面由设计方做，这里只是说明）

- 等挑方向时：`pending.kind = "setup_pitches"`，`pending.open = true`。界面据此显示「聊定的会直接写进去」，书有定调时显示〔补齐开书稿〕（调 `action = "fill"`）。
- 开书写的过程中：`book.setup_progress.pieces` 照旧报告三块的 `drafting`／`confirmed`，界面用它在标签上显示「正在写」。
- 写完：书 `status = "ready"`，任务成功结束；界面显示〔开写〕。

## 7. 测试

后端测试至少覆盖（演示模式，不调真实模型）：

1. 等挑方向时，群聊说「把主角的性格改成冷静隐忍」→ 直接改了那张卡片，消息结果是 `edit`、能撤销；任务仍在等挑方向。
2. 等挑方向时，群聊说写作要求 → 记成要求；提问 → 回答；说「都不满意，再来三个」→ 409 `use_feedback`，前端照旧交给重出。
3. 等挑方向时方案卡照办：定调写进去了、新建的设定条目都在、要求记下了，任务仍在等挑方向，主编说了 1.3 那句话；不会重出三个故事方向。
4. `fill`：没有定调时 422；有定调时一路写到 `finalize`，中间没有任何 `setup_piece` 等待，定调的一段话逐字不变，书 `ready`，提醒变成了待处理的建议，有决定时发了 3.3 那条消息，结束语是 3.4 那句。
5. `pick` 之后中间也不停；一口气模式从头到尾一次都不停。
6. 检查点里没有 `piece_gates` 的旧任务停在 `setup_piece`：照旧等确认，确认后照旧往下走。
7. 新建任务传 `prefill=True` 也直接出三个故事方向；已经停在 `setup_prefill` 的旧任务点「出三个故事方向」照旧能走。
8. 等挑方向时 `rewrite_target`（改一处）能用；等大纲确认时照旧被拦住。

## 8. 验收

- 在独立的数据库、Redis 库和端口上用演示模式走一遍（只用接口，不用截图）：新建书 → 等挑方向 → 群聊里改一处 → 出方案卡并照办 → `fill` → 写完 → 开写前 3 章。把每一步的请求和结果摘要写进 `docs/第三包验收.md` 新的「补丁 2」小节。
- 不要运行 start.ps1，不要升级、重启或改动日常的 8000／4320 服务和书库。
- 设计说明第 3.1 节和第 13 节里「定调和设定库合并确认一次，再出大纲，再确认大纲」的说法，按本补丁改成：挑方向这一步敞开；挑了方向或补齐以后一口气写完，中间不停；只剩「开写」一个决定；已经停在确认那一关的旧任务照旧。
