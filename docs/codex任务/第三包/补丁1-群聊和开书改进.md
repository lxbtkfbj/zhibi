# 补丁 1：群聊提速、定案，定调和设定库合成一步

> 先读 `docs/codex任务/第三包/README.md`、`3-开书新三步.md`、`6-和编辑部聊天.md`（第三包六个任务都已完成并提交）。本补丁改会议室的聊天和开书的前两步，不动写作流程。

## 为什么改

1. **群聊慢**：作者在群聊发一句话，`POST /books/{id}/notes` 要先用**主编的模型**调一次 `library_route`，判断是哪一种话，判断完才返回。主编通常配的是最强、最慢的模型，作者要干等几秒到十几秒，页面上什么也没有。
2. **聊定了落不了地**：作者想先在会议室和编辑部畅所欲言，理清思路后说「总结一下」，看过没问题再说「就按这个来」。现在：
   - 「总结一下」只得到一段普通的回答；
   - 「就按这个来」交出去的只有这几个字：等确认时当成修改意见，重出的那一步看不到前面聊了什么；平时会记成一条没头没尾的作者要求；
   - 私聊的〔照这个改〕只把结论压成 80 字以内的一句话，细节大部分丢了；
   - 主编还会说「群里定下来，咱们就直接排第一卷开篇章纲」这类话，其实聊天里说的什么都没生效。
3. **定调和设定库硬排了先后**：开书必须先确认定调，主编才开始建设定库。可很多时候作者是先有一个抓人的设定（金手指、境界、秘密），再围着它想故事，或者两边一起改。现在作者虽然能先进设定库自己写，但出故事方向、写定调、建设定库时，主编都不看已有的设定：定调可能和它对不上，建库时还可能再建一个不同名字的主角。
4. **「短版」看不懂**：作者第一眼以为是「短板」（缺点），不知道是三个可选的故事方向。

这个补丁做四件事：

- **提速**：加一个可以单独配快模型的「群聊分流」角色；明显的提问跳过判断；群聊的话发出去马上显示，判断放到后台（第 1–3 节）。
- **定案**：作者让编辑部「总结一下」，得到一张能改的**方案卡**；点〔按这个来〕或说「就按这个来」，按书现在的状态整张落地；私聊也一样（第 4–8 节）。
- **定调和设定库合成一步**：挑完故事方向，主编写定调、紧接着建设定库，中间不停；作者两边按任意顺序看、改，确认一次就去出大纲。也可以先写设定再出故事方向；主编每一步都看已有的设定（第 9–11 节）。
- **「短版」改叫「故事方向」**（第 12 节）。

规则不变：群聊仍然分三种话，拿不准仍按提问闲聊处理；私聊里聊天本身不改东西、不记要求。

## 1. 「群聊分流」角色

- 后端 `app/models/llm.py` 的 `ROLES` 加 `"router"`（加在最后）；模型设置接口照常返回和保存它。
- 前端 `lib/roles.ts` 的 `ROLE_KEYS` 加 `router`，显示名「群聊分流」。模型设置页里它排在最后，说明文字：`判断你在群聊里说的话是要改设定、记成要求还是提问。选一个快的模型就行，不用最强的。没选时用「默认」的模型。`
- 没给它配模型时用「默认」的模型（`LLMRouter.resolve` 已经是先找角色、再找 `default`，不用改），**不再跟着主编**。
- 凡是调 `library_route` 的地方（群聊判断、任务 3 设定库这一步的「提意见」）都改用 `router` 角色的模型；系统提示仍用 `persona("chief")`（不新建 `persona_router.md`）。调用记录的 `purpose` 写 `群聊分流`。

## 2. 作者的话先过程序判断

群聊和私聊的话，先按下面的顺序过程序判断（`app/services/chat_context.py`），命中一条就不往下走，**都不调模型**：

1. **要总结**（`wants_plan(text)`）：去掉标点后不超过 40 字，并且含 `总结`、`归纳`、`汇总`、`整理一下`、`整理成方案`、`列个方案`、`出个方案` 之一 → 出方案卡（第 4 节）。
2. **照方案办**（`accepts_plan(text)`）：去掉标点后不超过 20 字，并且含 `按这个来`、`按这个办`、`照这个来`、`照这个办`、`就这么定`、`就这样定`、`就按这个`、`按方案来`、`就按方案`、`照方案` 之一：
   - 这个对话（群聊或这个私聊）里有一张还没落地的方案卡 → 把最新的那张落地（第 6 节），作者的消息 `outcome = {"kind": "plan_apply", "plan_id": …}`，显示「照方案办：{方案名}」；
   - 没有 → 不记、不改，由主编回：`还没有方案可以照办。想让我把前面聊的整理成方案，就说「总结一下」。`（`outcome = {"kind": "chat"}`）。
3. **明显的提问**（`obvious_question(text) -> str | None`，只用于群聊）：去掉末尾空白后以「？」或「?」结尾，并且**不含**下面任何一个词：`改`、`换`、`加`、`删`、`去掉`、`别`、`不要`、`以后`、`下一`、`从现在`、`帮我`、`记下`、`记住`、`照这个`、`按这个`。
   - 例：「楚风现在什么境界？」「第三个单元为什么这样安排？」算；「下一章节奏快一点，行吗？」「把境界名称换一套好不好？」不算。
   - 谁来回答（按顺序找，找到就停）：含 `境界`、`设定`、`在哪`、`谁知道`、`前后` 的，设定师；含 `怎么写`、`文风`、`示范`、`写法` 的，写手；含 `毛病`、`不好看`、`漏洞`、`问题` 的，审稿；其余主编。
   - `outcome = {"kind": "chat", "shortcut": true}`，之后和模型判断出的提问闲聊完全一样（任务 6 第 4 节的回答流程）。
4. 都没命中：私聊照任务 6 当成聊天回答；群聊交给模型判断（第 3 节）。

这道判断在书的任何状态（空闲、编辑部在工作、等作者拍板）都先走：总结、照方案办、明显的提问在等拍板时也照常处理，不返回 409。判断错了，作者点任务 6 已有的〔其实要记下〕就行。

## 3. 群聊发出去立刻显示

### 3.1 空闲、编辑部在工作时：先存再判断

1. 群聊的话没被第 2 节截下来：先把作者的消息存进群聊，`payload.outcome = {"kind": "pending"}`，`job_id` 为空，**马上返回**（仍是 201）。
2. 判断放到后台（`BackgroundTasks`）：调 `library_route`，按任务 6 第 2.2 节的表格处理，处理完把这条消息的 `payload.outcome` 改成最终结果；需要交给流程的（`to_job`、开书中的改设定），这时再把消息的 `job_id` 设成那个任务。每次改完发 `message_update` 事件（任务 6 已有）。
3. **同一本书的群聊判断排队做**：用 Redis 锁，按消息 id 从小到大一条一条判断，保证流程读插话的先后顺序不乱（流程按消息 id 读插话，前一条还没设上 `job_id` 时后一条不能先设）。
4. 判断时按**判断那一刻**的书的状态处理（任务 6 已有这层复核，保留）。这时如果书已经进入等作者拍板、而结果是改设定或写作要求：不当成修改意见，`outcome` 改成 `{"kind": "too_late"}`，显示「编辑部这时在等你拍板，这句话没有记，也没有改。要改的话，在拍板的地方提意见，或者让我总结成方案。」不带按钮。
5. 判断出错（模型出错、超时 60 秒）：`outcome` 改成 `{"kind": "failed", "reason": "…"}`，显示「没判断出来（{原因}），这句话没有记，也没有改。」，带任务 6 的〔其实要记下〕。不重试，不当成修改意见。

### 3.2 等作者拍板时：当场判断

等作者拍板时（任务处于 `waiting_author`），没被第 2 节截下来的群聊的话照任务 6 当场判断（改用 `router` 的模型）：

- 提问闲聊：回答。
- 改设定、写作要求：
  - **刚才在聊**（这个任务最近一次等作者以后，群聊里已经有过聊天回答，即 `payload` 有 `reply_to` 的消息）：不返回 409，改为直接出方案卡（第 4 节），把作者这句话当成总结的要求一起交给模型；作者消息的 `outcome = {"kind": "plan_made", "plan_id": …}`，显示「刚才聊了不少，我先整理成方案，你看看再照办」。这样「就用方向一」不会被单独交出去、丢掉前面聊的内容。
  - **没聊过**：照旧返回 409 `use_feedback`，前端把这句话当成修改意见交给对应的接口。

### 3.3 前端

- 消息下面 `outcome.kind = "pending"` 时显示一行淡色的「主编在看…」（带三个点的小动画，遵守减少动效），收到 `message_update` 后换成最终结果。
- 新增结果的显示：`too_late`、`failed`、`plan_apply`、`plan_made`（文字见上）。
- 群聊发送按钮：除了等拍板时，发出去马上清空输入框、恢复可输入，不再等判断。
- `pending` 超过 2 分钟没有变（比如后台进程重启了），显示成 `failed`，原因写「判断超时」。
- 后端启动时把还是 `pending`、存在超过 2 分钟的群聊消息改成 `failed`（原因「判断中断」），免得永远停在「主编在看…」。

## 4. 方案卡

### 4.1 什么时候出

- 作者说「总结一下」这类话（第 2 节第 1 条）；
- 每个对话（群聊、每个私聊）顶上，〔换个话题〕旁边新加〔总结一下〕按钮：点了等于作者说「总结一下前面聊的」（作者消息照常存进对话）；
- 等拍板时刚聊过又交代了修改（第 3.2 节）。

方案卡在后台生成，期间照任务 6 发 `chat_typing`，显示「{角色名}正在整理方案…」。

### 4.2 结构化产出（`app/agents/schemas.py`，逐字照抄，字段顺序照抄）

```python
class PlanItem(Lenient):
    where: Literal["定调", "设定库", "大纲", "写作要求"] = Field(
        description="这一条落在哪：定调的一段话；设定库里的一条；大纲里的篇、卷、单元或结局；以后规划和写作都要照做的写作要求"
    )
    target: str = Field(
        default="",
        description="设定库写条目或角色卡片的名称（照设定库目录，新建的写新名字）；大纲写「第 N 篇」「第 N 卷」「单元「名称」」或「结局」；定调、写作要求留空",
    )
    part: str = Field(
        default="",
        description="设定库才写：改这一条的哪一处，卡片的字段名、等级的级名、「一句话」「一段话」；新建的和整条都要改的留空",
    )
    category: str = Field(
        default="",
        description="设定库里新建的才写：放进哪一类，七个默认类别之一（角色卡片、等级体系、世界与地图、势力划分、物品与功法、往事与秘密、特殊规则）或已有的自建类别",
    )
    change: str = Field(
        description="要落实成什么，写清楚具体内容，不看前面的对话也能照做；不要写「方向一」「刚才说的那个」，要把内容写出来"
    )
    scope: Literal["一直有效", "只管下一章", "只管这一卷", "只管下一卷"] = Field(
        default="一直有效", description="写作要求才看：作者说了只管下一章、这一卷、下一卷的照选，没说的选一直有效"
    )


class ChatPlan(Lenient):
    title: str = Field(description="方案名，4-12 字，如「开篇和老怪」")
    summary: str = Field(description="一段话说清和作者商量定了什么，100-300 字，给作者看")
    items: list[PlanItem] = Field(
        default_factory=list,
        description="要落实的条目，按定调、设定库、大纲、写作要求的顺序排；只放作者提出或明确同意的，最多 12 条；什么都没定就留空",
    )
    open_questions: list[str] = Field(
        default_factory=list, description="聊到了、但作者还没拍板的问题，每条一句；没有就留空"
    )
```

### 4.3 生成

调 `chat_plan`（第 9 节），角色：群聊用主编，私聊用那个角色；系统提示用这个角色的 `persona`。变量：

| 变量 | 内容 |
|---|---|
| `who` | 角色名；群聊写「编辑部」 |
| `concept`、`library`、`outline`、`progress`、`pending` | 同任务 6 第 4.3 节 |
| `summary` | 这个对话的摘要；没有写「（没有）」 |
| `recent` | 这个对话最近 30 条，拼法同任务 6 第 4.7 节，合计上限改为 12000 字 |
| `note` | 作者这次说的（按钮触发的写「总结一下前面聊的」） |

- `items` 和 `open_questions` 都是空的：不出卡片，由这个角色回：`前面还没聊出要落实的东西。想好了再叫我总结。`
- 否则发一条消息：`kind = "plan"`，说话人是这个角色，`payload = {"thread"（私聊才有）, "plan": ChatPlan, "status": "open", "results": []}`，`content` 写成纯文字版（第 4.4 节的格式，供摘要、导出和旧页面用）。
- 同一个对话里，新的方案卡出来以后，之前还是 `open` 的方案卡改成 `superseded`（发 `message_update`）。
- 方案卡算进对话（任务 6 第 4.7 节的 `dialogue`）：作为这个角色说的话，内容用纯文字版。

### 4.4 卡片的样子

```
方案：{title}
{summary}
· 定调：{change}
· 设定库 · {target}（新建 · {category}）：{change}
· 设定库 · {target} · {part}：{change}
· 大纲 · {target}：{change}
· 写作要求（{有效范围}）：{change}
还没定的：{open_questions，用分号连}
```

（没有 `part` 的不写那一段；不是新建的不写括号；没有 `open_questions` 不写最后一行。）

页面上：

- 每一条一行，右边一个 ×（删掉这一条）；点这一条的文字可以就地改 `change`（一个文字框）。改和删只在页面上，点〔按这个来〕时随请求一起交上去。
- 底下〔按这个来〕〔接着聊〕：〔接着聊〕只是把焦点放回输入框，卡片保持 `open`。
- 编辑部正在工作（排队或进行中）时，〔按这个来〕可点，但卡片上方提示「编辑部正在写，要改设定和大纲的几条会先放进待处理的建议」。
- `superseded` 的卡片变淡，标「已有新的方案」，没有按钮。

## 5. 私聊的两个按钮换掉

- 任务 6 第 3 节私聊最新回复下面的〔记成要求〕〔照这个改〕去掉；`POST /books/{book_id}/chat/{thread}/conclude`、`ChatConclusion`、`chat_conclude.md`（`git rm`）、catalog 里的登记一起删掉。
- 「要记下的要求」小框保留（〔其实要记下〕〔改一下〕还在用）。
- 私聊顶上那句说明改为：`这里只聊天，不会改动书稿，也不会记成要求。聊出想法以后说「总结一下」，看过方案再点「按这个来」。`
- 回答时的 `how_to_apply`（任务 6 第 4.3 节）私聊和群聊都改为：`作者想让聊出来的想法生效，要先让你「总结一下」出一张方案卡，看过再点「按这个来」。聊到想法差不多成形时，可以提醒他一句；不要说「就这么定了」「咱们直接开始排……」，聊天里说的都还没生效。`

## 6. 按这个来：落地

`POST /plans/{message_id}/apply`，请求体可带 `{"items": [...]}`（作者在卡片上改过、删过的条目；不带就用原样）。卡片必须是 `open`，否则 409「这个方案已经处理过了」。先把卡片改成 `applying`，马上返回；落地放到后台，**一条一条做**，每做完一条在 `payload.results` 里加一条结果并发 `message_update`；全部做完改成 `applied`。

按开始落地那一刻的书的状态，分两种：

### 6.1 等作者确认、而且这一步能接修改意见时：整张交给这一步

| 在等 | 交给 |
|---|---|
| 三个故事方向（`setup_pitches`） | 重出（`redo`） |
| 大纲这一块（`setup_piece`，块是 `outline`） | 提意见（`revise`） |
| 定下一篇（`segment_review`） | 提意见（`revise`） |
| 卷纲（`volume_review`）、单元章纲（`chapters_review`） | 提意见（`revise`） |

- 交出去的意见是下面这段（逐字照抄拼法）：

  ```
  【和作者商量定的方案：{title}】
  {summary}
  要落实的：
  - {第 4.4 节每一条的写法，不带开头的「· 」}
  还没定的（先不用管）：{open_questions，用分号连}
  ```

  （没有 `open_questions` 不写最后一行。）
- 抽出各接口里「交意见、恢复流程」的那段做成函数，接口和这里共用；这里调用时**不把整段意见记成作者要求**，只把「写作要求」那几条按各自的有效范围记下（`source = plan`）。
- 结果一条：`{"kind": "feedback", "label": "已交给编辑部：{重出三个故事方向／改大纲／重出这一篇／改卷纲／重出章纲}"}`；写作要求那几条各一条 `requirement` 结果（第 6.3 节）。

### 6.2 其余情况：一条一条落地

包括：空闲；编辑部在工作；先写设定（`setup_prefill`）；等作者确认、但不是上表那几种（定调和设定库这一关、试读、写不过去的章节）。

| 条目 | 做什么 |
|---|---|
| 写作要求 | 记成作者要求（`change`，有效范围照 `scope`，`source = plan`） |
| 设定库，找得到这一条（按名称和别名，同任务 2 的 `find_target`） | 照「照作者的意思改」改那一处（任务 2 的 `rewrite_target`，`mode = instruction`，`instruction = change`，路径照任务 2 的 `route_path(target, part)`）；连带建议照常挂 |
| 设定库，找不到这一条 | 新建：类别用 `category`（对不上的放进特殊规则）；角色卡片：`name = target`、`one_line` 取 `change` 第一句、`background = change`；其余：`name = target`、`one_line` 取第一句、`content = change`；`status = 'must'`、`source = 'ai'`，记一版 |
| 定调 | `rewrite_target`（`target_type = concept`，`path = story`，`instruction = change`） |
| 大纲 · 第 N 篇 | 第 N 篇已规划的：改它的一段话（`segment`，`path = text`）；还没规划的：挂建议（见下） |
| 大纲 · 第 N 卷 | 改这一卷的一段话（`volume`，`path = summary`） |
| 大纲 · 单元「名称」 | 按名称找单元，改它的一段话（`unit`，`path = summary`） |
| 大纲 · 结局、或者对不上的 | 挂建议（见下） |

- **改不了的挂建议**：目标锁住、大纲那一处已经开写、编辑部正在工作时的设定库和大纲条目、对不上的大纲条目：挂一条建议，`kind = 'chat'`，`op = note`，标题 `方案「{title}」里的：{这一条的写法}`，结果 `{"kind": "suggestion", "suggestion_id": …}`。编辑部正在工作时，写作要求照记。
- 每做一条之前重新看一眼书的状态：中途开始工作了，剩下的设定库和大纲条目改为挂建议。
- 某一条出错（模型出错、原文对不上）：这一条结果 `{"kind": "failed", "reason": …}`，接着做下一条；不重试。

### 6.3 结果和撤销

卡片下面逐条显示结果：

| 结果 | 显示 | 按钮 |
|---|---|---|
| `requirement`（`requirement_id`） | 已记成要求（{有效范围}） | 〔撤销〕〔改一下〕（同任务 6） |
| `edit`（`target_type`、`target_id`、`target_label`、`revert_version_id`） | 已改：{target_label} | 〔去看看〕〔撤销〕（同任务 6 的 `edit`） |
| `created`（`target_type`、`target_id`、`snapshot`） | 已新建：{类别} · {名称} | 〔去看看〕〔撤销〕：这一条还和建好时一样才删（`DELETE` 现有接口）；改过了显示「已经改过，去设定库处理」 |
| `suggestion`（`suggestion_id`） | 放进了待处理的建议 | 〔去看看〕 |
| `feedback`（`label`） | {label} | |
| `failed`（`reason`） | 没做成：{reason} | |

全部做完，这个角色在对话里说一句：`方案「{title}」照办了：改了 {E} 处，新建 {C} 条，记了 {R} 条要求，{S} 条放进了待处理的建议。`（数字为 0 的那一段不写）；交给某一步的说 `方案「{title}」交给编辑部了：{label}。`

## 9. 定调和设定库合成一步

### 9.1 流程

开书从三道关变成两道：**挑故事方向 → 定调和设定库 → 大纲**。

- `piece_gate` 在定调这一块（`concept`）不再停：和一口气模式一样，保存、检查完就接着建设定库（`settings_focus` → `settings_rest`）。设定库那一块的 `piece_gate` 是这一关唯一的一次停，作者确认时定调和设定库一起记为已确认（`setup_progress` 两块都是 `confirmed`）。
- 这一关的 `pending`：沿用 `{"kind": "setup_piece", "piece": "settings", …}`，另加 `concept_warnings`（定调的程序检查提醒，任务 3 第 3.3 节）和 `concept_decisions`（定调替作者做的决定）；原来的 `warnings`、`decisions`、`summary` 是设定库的。
- 一口气模式不变（照旧停在大纲）。
- 定调写好、保存以后马上发进度事件，作者在主编建设定库的时候就能读到定调（这时编辑部在工作，还不能改）。
- 升级前停在定调那一关的开书任务：作者确认以后照新流程接着建设定库，到设定库那一关再停。

### 9.2 这一关作者能做的

- **确认**：页底按钮「定调和设定先这样，去出大纲」，定调页和设定库页都有，点哪个都一样。
- **直接改**：定调页、设定库页照任务 4 的做法改（改这一句、给我几个写法、自己改、锁住……），不分先后。改了定调，照任务 3 第 6.3 节给设定库和大纲挂「定调改了」的建议。
- **换决定**：定调页显示 `concept_decisions`，设定库页显示 `decisions`。换定调的决定，照下面「提意见」里定调那部分处理，意见写「把「{话题}」改成「{选择}」」；换设定库的决定照原来的做法。
- **提意见**（`revise`）：先调 `setup_notes`（`done` 里放定调和设定库），拿到 `SetupNotePlan`：
  - `concept_instructions` 不空：照「照作者的意思改」改定调的一段话（任务 2 的 `rewrite_target`，`target_type = concept`，`path = story`，`instruction` 用它）；底牌、基本信息里要改的，挂成建议（`kind = 'review'`，`op = note`，标题「{要改的内容}」），由作者在定调页自己改；
  - `settings_instructions` 不空：照任务 3 第 6.2 节设定库那一行的做法；
  - `outline_instructions` 不空：记成作者要求（`source = note`），出大纲时照办；
  - 做完回到这一关的等待，`pending` 里带上最新的 `summary`。

### 9.3 页面

- 开书进度条：定调、设定库两块在这一关都显示「待你确认」，点哪块打开哪页。
- 自动跟随：这一关打开定调页；定调页顶上一行「设定库也建好了：{summary}」和「去看看」。
