# 主编手册：共同约定

这一包给编辑部加「手册」（作者叫它 skill）：一本手册是一类问题的专业经验，群聊里模型看目录，自己用工具翻需要的那本，再照作者问的回答。以后加手册只放一个文件，不改程序。

本包的任务都照这一份约定，不照别的目录的 README。

1. 先读本文件，再读任务文件。
2. 开工前 `git status` 不干净就停下来问，不要动、也不要替别人提交没提交的改动。
3. 界面上的字逐字照任务文件；没写到、你自己补的字列进验收说明。提示词只照任务给的草稿搬（`git mv -f`，逐字节不改），其余提示词一个字不改。
4. 不要升级、重启或改动作者日常的 8000／4320 服务、日常 worker 和书库，不对日常环境运行 `start.ps1`／`stop.ps1`。验收用独立的数据库、Redis、端口、worker。**不调真实模型。**
5. 什么时候自己定，什么时候停下来问：
   - 自己定，做完在完成说明里单独列出来：
     - 测试里写死的旧指纹、旧文字和开工时 HEAD 的提示词或代码对不上，而那份文件本任务没动过（和开工时 HEAD 逐字节一致）：改测试跟上 HEAD，提示词和代码都不动。
     - 和本任务无关、开工前就坏了的测试：修法是机械的（同上一条），直接修；要改产品代码或者改变行为才能修好的，停下来问。
     - 任务没写到的实现细节：函数怎么拆、文件放哪、内部怎么命名、测试怎么组织。
   - 停下来问：
     - 要改任务没让改的提示词，或者要动任务写死的界面文字、行为、数据结构；
     - 任务的要求和现有代码真的打架，两种做法都说得通，而且会影响作者怎么用；
     - 要放宽阈值、加遮挡、删测试或跳过测试才能过；
     - 要动作者日常的服务和书库，或者要调真实模型；
     - git status 不干净（第 2 条）。
6. 检查：开发中只跑相关测试；提交前跑一次全量，全部通过。
   - 后端（`backend/`）：`uv run ruff check . && uv run ruff format --check . && uv run pytest -q`
   - 前端（`frontend/`）：`npx tsc -b && npm run lint && npm run build && npm run test:workspace`
   - 页面比对：精髓 28 组（`frontend/tests/essence-parity.browser.mjs`）、装修 16 组（`frontend/tests/desk-v2-parity.browser.mjs`）重跑，全过，不加遮挡、不放宽阈值。
7. 验收写在 `docs/主编手册验收.md`，每个任务一节；截图放 `docs/主编手册验收/`，少而准。
8. 直接在当前分支上做，不推送。提交信息以「主编手册：」开头。
9. 做完用一段中文告诉作者：改了哪些文件、测试和全量检查结果、截图在哪、自己补的字。
