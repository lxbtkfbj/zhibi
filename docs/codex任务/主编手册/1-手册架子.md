# 主编手册 任务 1：搭手册的架子

共同约定照本目录的 `README.md`。

## 为什么做

作者觉得主编在群聊里的回答不够在行。做法：编辑部有一套「手册」，一本手册是一类问题的专业经验（比如「开书」）。群聊里模型看得到手册目录，用得上就自己调工具翻那一本，拿到全文再答。以后加手册只放一个文件，不改程序。

设计方 2026-10-22 实测过（只读，没改配置、没写库）：

- 作者的两个模型都能调工具：主编用的「【Alicia】gemini-4」和默认的「【Alicia】gemini-3.8-flash」。
- 用《佔位》真实的群聊提示词（chat_agent）、群聊真用的查资料工具，再加一个 `read_skill`，目录里放三本手册。8 道题各问两次，16 次都挑对：
  - 开书的问题（包括「书快写完了，随口问一句开书」）都去翻了「开书」；
  - 问「设定库里有哪些人物」，没翻；
  - 问「打斗怎么写才燃」，翻了「打斗」。

现在用不上，是因为一个开关把两件事绑在了一起：

- 群聊能不能调工具（`chat_agent.supports_tools`）看的是 `structured_method != "json_mode"`。
- 3.8f 是 10-14 开书时用「强制调某个工具」出结构化结果，被渠道拒了，程序自动改成 JSON 模式（`structured_method_auto = true`）。gemini-4 是手动选的 JSON 模式。
- 两个配置因此连群聊的工具也关了。实测 3.8f 普通调工具（不强制）完全没问题，被拒的只有强制调工具。

## 1. 手册文件

- 目录 `backend/app/prompts/skills/`，一本手册一个 `.md`，文件名是英文小写 key（只用 `a-z`、`0-9`、`_`，字母开头）。
- 格式：第一行 `# 名称`；正文里有一行以「什么时候翻：」开头（目录里用这一行冒号后面的字）；其余是正文。不允许 `{{变量}}`。
- 先放一本：把 `docs/codex任务/主编手册/提示词/skills/opening.md` 用 `git mv -f` 搬到 `backend/app/prompts/skills/opening.md`，逐字节不改。
- 提示词名称是 `skills.<key>`：`app.prompts.canonical_name` 放行 `skills.` 前缀（和现在的 `playbooks.` 一样）。读手册一律走 `app.prompts.load`，作者在提示词页改过的版本优先。打包照 `playbooks` 目录一样带上。
- 加手册：放一个文件、重启服务，不改程序。

## 2. 提示词页能看、能改

- 提示词页自动列出 `skills/` 里的每一本，不用往 `CATALOG` 里手写条目：
  - 分组「手册」；
  - 中文名取 `# 名称`；
  - 使用时机写「群聊里编辑部自己翻：」加「什么时候翻：」后面的字；
  - 角色写 `chief,lorekeeper,writer,reviewer`。
- 保存时校验，不过就拒绝，并说清缺什么：
  - 第一行必须是 `# 名称`；
  - 必须有「什么时候翻：」那一行；
  - 名称不能和别的手册重名；
  - 不能有 `{{变量}}`。

## 3. 翻手册的工具 `read_skill`

- 只要至少有一本手册，新书群聊（`chat_agent` 那条路）给模型的工具里就加上 `read_skill`。只问不改（ask_only）时也有。拆的书群聊这次不加，私聊这次不动。
- 工具定义照下面这个样子：
  - 描述第一句固定；
  - 后面是程序拼的目录，每本一行「- 名称：什么时候翻」，按文件名排序；
  - `name` 的 `enum` 是所有手册的名称，顺序同目录。

```json
{
  "type": "function",
  "function": {
    "name": "read_skill",
    "description": "翻编辑部的专业手册，拿到全文再答。手册目录：\n- 开书：作者问到怎么开一本新书，或者想定、想改一本书的世界观、主角、金手指、核心循环这些根基。",
    "parameters": {
      "type": "object",
      "properties": {"name": {"type": "string", "enum": ["开书"], "description": "手册的名称，照目录写"}},
      "required": ["name"]
    }
  }
}
```

- 执行：
  - 照名称找到那本，把全文交回给模型（作者改过的版本优先）。
  - 名称不对，交回「没有这本手册：{名称}。目录里有：开书、……」，不抛错。
- 显示：
  - 回答框里那一行写「在翻《开书》」；
  - 回答下面「查了：」里那一项写「手册《开书》」。
  - 重新回答时照旧带上这一轮查到的东西（含手册全文）。

## 4. 「群聊能不能调工具」和「结构化输出方式」分开

1. `llm_profiles` 加一列 `chat_tools`（可空布尔，新迁移 0027）：
   - 空：没试过，照常让它调，不认就退回老路；
   - `true`：测试时调成功过；
   - `false`：群聊里调工具被拒过，或者测试时没调、出错。

   已有的配置都留空。升级、降级都能跑。
2. `supports_tools`：演示模式、本机模型照旧。其余只看 `chat_tools`，不再看 `structured_method`：`chat_tools` 是 `false` 才不给工具。
3. 群聊调工具被接口拒（`LLMRouter.tool_rounds` 里现在调 `_remember_structured_method(profile, "json_mode")` 那段）：
   - 改成只记 `chat_tools = false`，加和现在一样的保护：作者正在改的配置不覆盖；
   - `structured_method` 不动；
   - 照旧抛 `ToolsUnsupported`，这句话改走分流。
4. 结构化输出降级（改用 JSON 模式并记 `structured_method_auto`）照旧，不碰 `chat_tools`。
5. 系统设置的「测试」（`tool_support`）：
   - 不再因为是 JSON 模式就跳过工具测试，照样真叫它调一次 `look_up`；
   - 结果写回 `chat_tools`：调了是 `true`，没调或出错是 `false`；
   - 演示模式、本机模型照旧不测。
6. 改了提供方、接口地址、模型或密钥：`chat_tools` 清空。就在现在清 `structured_method_auto` 的同一处。
7. 接口返回的配置带上 `chat_tools`，前端类型跟着加。

界面的字（`SettingsPage.tsx` 和 `tool_support` 的返回文字）逐字照下面改：

- 现在这句：「这个接口不认工具调用，已自动改用 JSON 模式：群聊里编辑部不会自己查资料、动手，先判断要做什么，再一件件做。」
  改成：「这个接口不认强制调工具，出结构化结果已自动改用 JSON 模式；不影响群聊里调工具。」
- `chat_tools` 是 `false` 时，在同一位置加一句：「这个接口在群聊里调工具被拒过：编辑部不会自己查资料、翻手册、动手，先判断要做什么，再一件件做。点「测试」可以重新试。」
- 测试结果：
  - 调了：「能调工具：群聊里编辑部会自己查资料、翻手册、动手」；
  - 没调：「叫它调工具它没调：群聊里编辑部用它时会退回老办法，先判断要做什么，再一件件做」；
  - 出错：前缀照旧「调工具出错了：」；
  - 本机模型：「本机模型不让编辑部自己查资料、翻手册、动手（太慢）：群聊里先判断要做什么，再一件件做」；
  - 演示模式：照旧。
- 原来那句「这个接口以前不认工具调用，已改用 JSON 模式：……」删掉，JSON 模式不再跳过测试。

## 5. 提示词：只改这一处

把 `docs/codex任务/主编手册/提示词/chat_agent.md` 用 `git mv -f` 搬到 `backend/app/prompts/chat_agent.md`，逐字节不改。它只在「怎么做」里加了第 2 条（翻手册），后面的编号往后顺延一位。其余提示词一个字不改。

## 6. 演示模型

`demo.tool_turn` 里加一条规则，`FAKE_TOOLS` 默认仍是 `False`：
- 条件：作者这句话里有「开书」，工具里有 `read_skill`，这一轮还没翻过。
- 做法：先调 `read_skill`（name=开书）。拿到结果后照旧往下走（查设定、动手、说话），最后那段话里带上「翻了开书手册。」。

## 7. 这次不做

- 私聊、拆的书的群聊不接手册。拆的书群聊会因为第 4 节走上能查资料的那条路，这条路本来就做好了，只是不给 `read_skill`。
- 题材打法（`playbooks/`）不动。
- 不写别的手册。

## 8. 测试

1. 手册：
   - 目录照文件生成（名称、什么时候翻，按文件名排）；
   - 提示词页改过的版本优先，目录和全文都用改过的；
   - 一本手册都没有时，没有 `read_skill`。
2. 工具：
   - `read_skill` 的 `enum` 和描述里的目录对得上；
   - 只问不改时也有；
   - 拆的书群聊没有；
   - 翻到的是全文；
   - 名称不对返回第 3 节那句、不抛错；
   - 「在翻《开书》」「手册《开书》」两处文字对。
3. 开关：
   - `supports_tools`：JSON 模式且 `chat_tools` 为空 → `True`；`chat_tools = false` → `False`；本机、演示照旧。
   - `tool_rounds` 被拒：`chat_tools = false`，`structured_method` 不变，抛 `ToolsUnsupported`。
   - 结构化降级：`structured_method` 改成 `json_mode`，`chat_tools` 不变。
   - 「测试」：JSON 模式的配置也真测，结果写回 `chat_tools`。
   - 改提供方、地址、模型、密钥时清空 `chat_tools`；只改名称、温度这些不清。
4. 提示词：
   - `chat_agent.md`、`skills/opening.md` 和草稿逐字节一致，加进现有的提示词指纹测试；
   - 提示词页看得到「手册」分组和「开书」；
   - 保存缺 `# 名称`、缺「什么时候翻：」、和别的手册重名、带变量的，都被拒。
5. 演示：`FAKE_TOOLS` 打开时，群聊里问「开书先定什么」，演示模型先翻开书手册，回答下面「查了：」里有「手册《开书》」。
6. 迁移：0027 升级、降级都能跑，已有配置 `chat_tools` 为空。
