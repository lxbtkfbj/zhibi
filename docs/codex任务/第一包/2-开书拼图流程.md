### 1.1 落地时的程序规则

- **技巧名**：凡是带 `techniques` 的产出，保存前过一遍 `clean_techniques`（任务 1）。
- **节点 kind**：AI 的「开篇 / 节点 / 结局」对应数据库的 `opening / milestone / ending`。
  - 程序强制第一个为开篇、最后一个为结局。
  - 模型给了多个开篇或结局时，只保留第一个开篇和最后一个结局，其余改成节点。
- **人物锚点**：`node` 序号和人物名都要合法，不合法的丢弃。
- **信息差**：`knowers` 里的名字必须在人物表里，不在的去掉。
- **分卷**：`target_node` 超出范围的置 0，并写进提醒；`reaches_node` 为真但节点的约第几卷不是本卷时，以分卷为准，把节点的 volume 改成本卷。
- **揭晓**：`reveals` 里的 `ref` 必须在信息差表里，不在的丢弃。

## 2. 流程图（`app/graphs/book_setup.py`）

### 2.1 常量

```python
ORDER = ["concept", "spine", "lore", "outline", "threads", "first_volume"]   # 节点提前到设定之前
PIECES = {"concept": ["concept"], "nodes": ["spine"], "cast": ["lore"], "fill": ["outline", "threads"], "first_volume": ["first_volume"]}
PIECE_ORDER = ["concept", "nodes", "cast", "fill", "first_volume"]
PIECE_NAMES = {"concept": "定调", "nodes": "关键节点", "cast": "人物上轴", "fill": "填中间", "first_volume": "第一卷"}
```

- `TARGET_NAMES` 中 spine 改为「关键节点」，lore 改为「世界观、人物与信息差」，outline 改为「全书总纲」。
- `SYNC_INSTRUCTIONS` 按新顺序改写措辞（spine 要和概念一致；lore 要和概念、节点一致；outline 要和节点、人物锚点一致……）。
- `cascade()` 用新的 ORDER。逐块模式下，`cascade` 的下游只展开到当前块为止；后面的块还没做，等做到时自然按最新内容写。

### 2.2 状态（SetupState 新增）

| 字段 | 说明 |
|---|---|
| `mode` | `"puzzle"` / `"oneshot"`；缺省（旧检查点）按 oneshot |
| `directions` / `direction` | 方向列表 / 作者选定的方向（方向字段加上 `mix`、`length`） |
| `piece` | 当前块 |
| `pieces` | 各块状态：`todo` / `drafting` / `waiting` / `confirmed` / `done`（`done` 用于一口气模式：已做完，但作者还没逐块确认） |
| `decisions` | `{内部步骤: [AuthorChoice dict]}` |
| `warnings` | 当前块的程序提醒 |
| `suggestions` | 跨块审稿里针对已锁定部分的问题：`[{target, problem, suggestion}]` |
| `unlock_requests` | `[{target, reason}]` |
| `candidates` | `{"node_id": str, "nodes": [...]} \| None` |
| `node_snapshot` | 渲染节点相关提示词时的节点 ID 顺序，用于把模型返回的序号映射回 ID |
| `resync` | 重新打开某块后，后面需要按同步要求重检的内部步骤 |
| `piece_reviewed` / `piece_revised` | `{块: bool}`，每块的单块审稿和自动修改各最多一轮 |

`initial_state(idea, style, ask=False, mode="oneshot")`：

- puzzle：`queue=["concept"]`，`piece="concept"`，各块为 `todo`。
- oneshot：`queue=list(ORDER)`。

### 2.3 入口与路由

- `route_start`：puzzle → `directions`；oneshot → 原逻辑（`ask` 时走 `interview`，否则走 `intake`）。
- `route_next`：
  - 队列非空 → `queue[0]`。
  - 队列空了：puzzle → `piece_check`；oneshot → 原逻辑（`critique` 或 `persist`）。
- 每一步做完仍先经过 `intake`。

### 2.4 方向

- **`directions_node`**：
  - 状态「主编在想几个开书方向…」。
  - 调 `editorial.draft_directions`：提示词 `setup_directions`，变量为 `idea`、`style`、`requirements`、`glossary`。
  - 发言用 remark。
  - 产出卡片：`{"type": "directions", "data": {"directions": [...], "recommended": n}}`，标题「开书方向：3 个」。
  - 更新进度：`concept` → `drafting`。
- **`directions_gate_node`**：interrupt 之前不放任何有副作用的代码。

  ```python
  interrupt({"kind": "setup_directions", "directions": [...], "recommended": n, "length": LENGTH_QUESTION})
  ```

  恢复时：
  - `{"action": "choose", "choice": i, "mix": str, "length": str}` → 写入 `state["direction"]`，进入 `intake`（队列为 `["concept"]`）。
  - `{"action": "redo"}` → 回到 `directions_node`。作者的意见已经由接口记成作者要求，重新出方向时会读到。

### 2.5 各内部步骤

- **`concept_node`**：多了变量 `chosen_direction`。
  - 逐块模式下由 `format_direction_choice(direction)` 生成：

    ```
    【作者选定的方向】
    方向「名称」：一句话故事
    主角：……
    金手指：……
    开局：……
    卖点：……；……
    舞台阶梯：……
    基调：……
    目标读者：……
    ```

    有混搭要求时再追加一段「【作者的混搭要求】」加上原文。
  - 一口气模式下 `chosen_direction` 为空串。
  - `decisions` 存进 `state.decisions["concept"]`。
- **`spine_node`**：
  - 提示词 `setup_spine`，变量为 `concept`、`playbook`、`requirements`、`glossary`、`revision`。`playbook` 用新增的阶段 `nodes`：在 `playbook.STAGES` 里加 `"nodes": ("总则", "分卷", "线索")`。
  - 修改时 `revision` 里的当前版本用 `format_spine`，带铁钉 / 暂定 / 留空标记；同时记下 `node_snapshot`。
  - 产出经 `merge_nodes(ai_nodes, current_nodes)` 合并：
    1. `ref>0` 的，对应快照里第 ref 个节点：
       - 原节点是铁钉 → 内容一律保持数据库原样，只取它在新列表中的位置。
       - 原节点是暂定或留空 → 用新内容，保留原 id；状态：留空的变暂定，暂定的保持暂定；来源保持原样。
    2. `ref=0` 的新节点 → 暂定、来源 ai。
    3. 快照里的铁钉节点没被引用 → 按原来的相对顺序插回：放在原本在它前面、且仍在新列表里的那个节点之后。
    4. 快照里没被引用的暂定节点 → 删除。
    5. 强制开篇在首、结局在尾。
  - `decisions["spine"]`。
- **`lore_node`**：提示词 `setup_lore`，变量为 `concept`、`spine`、`requirements`、`revision`。锚点和信息差按 1.1 的规则校验。`decisions["lore"]`。
- **`outline_node`**：提示词 `setup_outline`，变量为 `concept`、`lore`、`spine`、`playbook`（outline 阶段）、`requirements`、`chapter_hint`、`glossary`、`revision`。
  - 长线伏笔：kind 为伏笔，span 为长。
  - 期待：kind 为期待。
  - 两者合在一起用 `assign_seqs` 编号（共用编号空间，内容相同的沿用原编号）。
  - `decisions["outline"]`。
- **`threads_node`**：提示词 `setup_threads`，变量为 `concept`、`lore`、`spine`、`outline`、`playbook`（threads 阶段）、`requirements`、`revision`。产出后由程序生成各卷的 `thread_beats`：把所有线索中 `volume == 卷号` 的节拍，按线索顺序写成 `[{thread: 线索名, beat: 节拍}]`。
- **`first_volume_node`**：`first_volume_blocks` 新增三个块：
  - `target_node`：`format_target_node(第一卷卡片, 节点)`，见第 4 节。
  - `secrets`：`format_secrets(全部信息差)`。
  - `glossary`：`glossary_block()`。

  原来 `story_so_far` 里的「开篇设计」取的是 `spine["opening"]`，现在改为取开篇节点的 event。

  产出处理：新埋伏笔和新立期待一起编号，用泛化后的 `attach_new_foreshadowings` 写进单元动作（编号前缀按 kind）；`reveals` 按规则校验；开书阶段忽略 `node_update` / `node_conflict`，只记日志。

### 2.6 逐块模式：检查、保存、等确认

一块的内部步骤全部做完后，依次经过三个节点。

**`piece_check`**：

1. 跑程序检查，结果写入 `warnings`：
   - **nodes**：
     - 开篇、结局各有一个。
     - 中间节点 6-12 个。
     - 前提、之后不为空（开篇的前提除外）。
     - 约第几卷不倒退、不超过 `target_volumes`。
     - 连续 3 卷以上没有节点。
     - 还有留空。
   - **cast**：
     - 每个主角、女主、反派至少一条锚点。
     - 丢弃了多少条不合法的锚点或知情人。
     - 信息差少于 4 条。
   - **fill**：
     - 章数合计等于计划。
     - 开篇之后的每个节点都有一卷 `reaches_node`。
     - 目标节点序号随卷号不倒退。
     - 长线期待少于 2 条。
     - 期待或伏笔的立下 / 埋下卷晚于兑现 / 回收卷。
   - **first_volume**：没有任何期待动作的单元。
2. 单块审稿：
   - `piece == "nodes"`，且书的设置 `volume_audit` 为真，且这一块还没审过：用 `critique_setup` 审「部分方案」，没做的部分传「（还没做）」。
   - `piece == "first_volume"`：总是审，审全部方案。
   - 审稿结果中，属于本块内部步骤的 high/medium 问题，且本块还没自动改过：按 `cascade`（只展开到本块）排进队列，标记已修改，回到 `intake`。
   - 属于已锁定部分的问题，写进 `suggestions`。
3. 进入 `piece_persist`。

**`piece_persist`**：

- 调 `setup_store.save_piece(piece)`，再把这块的数据从数据库读回状态，拿到 id 和编号。
- 存一份 `DraftVersion`：`source="ai"`，`note=f"piece:{piece}"`。
- 进度改为 `waiting`。
- 主编在群聊说一句：「第 N 块「名称」好了……请你看看，没问题就点「确认这一块」。」（有提醒时顺带一句最重要的）。
- 发一条状态消息「等你确认：名称」。

**`piece_gate`**：interrupt 之前不放任何有副作用的代码。

```python
interrupt({"kind": "setup_piece", "piece": piece, "round": round,
           "warnings": [...], "decisions": [本块各内部步骤的 decisions 合并],
           "suggestions": [...], "unlock_requests": [...], "candidates": candidates or None})
```

恢复后按 `action` 处理：

| action | 处理 |
|---|---|
| `confirm` / `delegate` | 若 `piece == "nodes"` 且数据库里还有留空节点：设 `op={"kind": "fill_all", "then": "confirm"}`，转 `node_op`。否则走「确认」流程（见表下）。`delegate` 的含义是「交给编辑部定」，处理和 confirm 相同，只是作者消息的文案不同 |
| `revise` | 见下方「修改」 |
| `candidates` | `op={"kind": "candidates", "node_id": ...}`，转 `node_op` |
| `fill` | `op={"kind": "fill", "node_id": ...}`，转 `node_op` |
| `reopen` / `unlock` | 见下方「重新打开」 |

**确认**：

1. 用 `load_setup` 把全部数据从数据库读回状态，作者手动改过的内容就生效了。
2. 本块进度改为 `confirmed`，内部步骤加入已锁定集合。
3. 清空 `warnings`、`suggestions`、`unlock_requests`、`candidates`。
4. `piece == "first_volume"` → 转 `finalize`。
5. 否则进入下一块：把它的内部步骤放进队列；凡是在 `resync` 里的，带上 `SYNC_INSTRUCTIONS` 以修改模式重做，并从 `resync` 里移除。然后转 `intake`。

**修改**（`{"feedback": str, "node_id"?: str, "flips"?: [{"topic": str, "choice": str}]}`）：

- 先拼修改要求：
  - `flips` → 每条写成「把「{topic}」改成「{choice}」」。
  - `node_id` → 按数据库当前顺序算出序号，前面加「只改节点 N「标题」：」。
- 只有 `node_id` 或 `flips`、没有其他意见时：要求直接交给本块的第一个内部步骤（fill 块是 outline，再展开到 threads）。
- 有一般意见时：调 `triage_feedback`，传入 `locked` 块（第 4 节）。
  - 本块内部步骤的要求进队列。
  - 产出的 `unlock_requests` 写进状态。
  - 没有任何可执行的要求、只有解锁请求时：主编说明「这需要改已经确认的「X」，要解锁的话点「解锁并修改」」，回到 `piece_gate`。
- `round += 1`，`phase = "author_revise"`，转 `intake`。

**重新打开**（`{"piece": X, "feedback"?: str}`）：

- X 必须是已确认、并且在当前块之前的块。
- X 和它后面直到当前块的内部步骤全部解锁；X 之后的块进度改为 `todo`；这些块里已经有内容的内部步骤记入 `resync`。
- 有 `feedback`（来自「解锁并修改」）：X 改为 `drafting`，带着要求进队列，转 `intake`。
- 没有 `feedback`：X 改为 `waiting`，直接转 `piece_gate`，让作者在页面上自己改，再确认。

### 2.7 节点操作（`node_op`）

`node_op` 是 AI 操作，提示词为 `setup_node_slot`，变量为 `concept`、`spine`、`slot`、`requirements`、`glossary`。

**`slot` 的写法**（序号按数据库当前顺序算）：

- 换候选：「替换节点 4「冰凰宗」（作者想换一个）。前一个是节点 3「回幻妖界」，后一个是节点 5「封神大会」。给出 3 个候选。」
- 补空位：「节点 4（目前留空），夹在节点 3「…」和节点 5「…」之间。补成 1 个节点。」
- 作者写了一句：「节点 4，作者写了一句：「中间要有一场宗门大比」。以作者的想法为核心，补成 1 个完整节点。」

**三种操作**：

- `candidates`：产出写进 `state.candidates`，回到 `piece_gate`。作者「用这个」时，由前端直接 PATCH 节点内容，不需要恢复流程。
- `fill`：恢复值里带 `feedback` 时，这就是作者在留空卡上「我自己写一句」写的话：先把节点的 `origin` 改为 `author`，`slot` 用「作者写了一句」的写法。然后把结果写进这个节点。状态：作者写了一句的，改为 `pinned`；否则改为 `pencil`。回到 `piece_gate`。
- `fill_all`：按顺序给每个留空节点各调用一次补空位，然后按 `then` 继续走「确认」流程。

每次操作，主编在群聊说一句（例如「节点 4 给你出了 3 个候选」）。

### 2.8 一口气模式

- 流程同现在，顺序按新的 ORDER；没有 `piece_gate`。
- 每个内部步骤做完，对应块的进度改为 `done`。
- 跑完全部步骤后，照原逻辑 `critique` → 必要时自动改一轮 → `persist`（全量 `save_setup`）→ `author_gate`。
- 铁钉在这个模式下照样生效：
  - `critique` 和 `triage` 都传入 `locked`（此模式下只列铁钉节点）。
  - 修改关键节点时一律走 `merge_nodes`，铁钉不变。
- 作者在 `author_gate` 等待期间可以在页面上钉节点；`author_gate` 本来就会从数据库重新读方案。
- 批准后各块进度改为 `confirmed`。

### 2.9 插话

`intake` 调用 `absorb_notes` 时传入 `locked`。

- 已锁定内部步骤的修改要求一律丢弃。
- 结果里的 `unlock_requests` 合并进状态，在下一次 `piece_gate` 时交给作者。
- 主编的回应里说明需要解锁哪一块。

### 2.10 进度与兼容

- `mark_progress(d, state)`：写入 `books.setup_progress = {"mode", "current", "pieces"}`，并发一个会让前端刷新书详情的事件（现有机制不够就新增 `book` 事件）。
  - 调用时机：开始、每块开始、`piece_persist`、确认、重新打开、`finalize`。
  - `finalize` 时各块进度全部改为 `confirmed`，`current` 置空。
- 旧检查点：状态里没有 `mode`（按 oneshot）、队列里是旧的步骤名、`spine` 是旧形状——都要能继续跑完。`spine` 遇到旧形状，用任务 1 的 `spine_from_legacy` 转换。
- `fill_missing_steps` 用新的 ORDER。

## 3. 任务接口

- **创建书**：`BookCreate` 增加 `mode: Literal["puzzle", "oneshot"] | None`，缺省时取新书默认的 `setup_mode`。`jobs.new_setup_job(book, ask, mode)` 把模式写进 `params`；worker 启动开书流程时把 mode 传给 `initial_state`。
- **`DECISION_KINDS`** 增加 `setup_directions`、`setup_piece`：等待期间插话接口返回 409，前端改走下面两个接口。
- **`POST /jobs/{job_id}/directions`**：请求体 `{action: "choose" | "redo", choice?: int, mix?: str, length?: str, feedback?: str}`。当前等待的不是 `setup_directions` 时返回 409。
  - choose：
    - 把篇幅记成作者要求，格式同原来的提问回答：「这本书打算写多长？——{length}」，来源 `answer`。
    - 把方向记成作者要求：「开书方向：选用「{name}」{；混搭：mix}」，来源 `answer`。
    - 作者消息：「选方向「{name}」。」，有混搭时附上原文。
  - redo：`feedback` 不能为空，记成作者要求（来源 `note`）；作者消息即 feedback。
- **`POST /jobs/{job_id}/piece`**：请求体 `{action, piece, feedback?, node_id?, flips?}`。
  - 等待的不是 `setup_piece` 时返回 409。
  - `reopen` / `unlock` 之外的动作，`piece` 必须等于当前等待的块，否则返回 409「这一块已经变了，刷新一下再试」。
  - `revise` 时 `feedback`、`node_id`、`flips` 至少要有一项，否则 422。
  - `revise` 和 `reopen` / `unlock` 的 `feedback` 记成作者要求，来源 `note`；每条 flip 记成作者要求「「{topic}」改成：{choice}」，来源 `answer`。`fill` 的 `feedback` 是作者写给这个节点的一句话，不记成作者要求。
  - 作者消息文案：

    | action | 文案 |
    |---|---|
    | confirm | 「确认「{块名}」，下一块。」 |
    | delegate | 「「{块名}」交给编辑部定。」 |
    | revise | feedback；只有 flips 时列出改动 |
    | candidates | 「给节点 N 出 3 个候选。」 |
    | fill | 「补上节点 N。」，带作者写的一句时为「节点 N：{那句话}」 |
    | reopen | 「重新打开「{块名}」。」，有意见时附上 |

  - 入队的恢复值带上 `"requirement_saved": True`，和现有接口一致。

1. **逐块模式完整路径**：
   - 选方向（含篇幅和混搭）→ 确认定调 → 节点块。
   - 通过接口：钉一个节点、改一个暂定节点的文字、作者新增一个节点（应为铁钉）、把一个节点设为留空。
   - 对一个节点要候选，然后 PATCH 用候选内容；再补空位。
   - 确认节点块 → 人物上轴 → 确认 → 填中间 → 确认 → 第一卷 → 跨块审稿给出建议 → 确认。
   - 结束时检查：书为 ready，第一卷为 approved，`setup_progress` 五块全部 confirmed；数据库里节点、锚点、信息差、卷的目标节点、E 编号的期待都正确。
2. **铁钉保留**：节点块作者意见要求改动一个铁钉节点以外的内容，铁钉节点逐字不变；模型漏掉铁钉节点时插回原位置。
3. **确认时补空位**：节点块确认时还有留空，会先补成暂定再进入下一块。
4. **解锁请求**：
   - 人物上轴阶段插话要求改概念（已锁定）→ 概念不变，等确认时带 `unlock_requests`。
   - 执行 `unlock` → 概念按理由修改；之后各块按同步要求重检，并逐块再确认。
5. **重新打开**：在填中间等确认时重新打开节点块（不带意见）→ 节点块回到等确认；确认后人物上轴、填中间按同步要求重做。
6. **一口气模式**：原有测试全部通过；作者拍板时提意见，铁钉节点不变。
7. **旧检查点**：用旧形状的状态（没有 mode、旧队列、旧 spine）恢复，能跑到等作者拍板。
8. **接口**：两个新接口的 409 / 422 规则；篇幅、方向、flips、意见都记成作者要求，来源正确。
9. **`plan_volume` 两处调用**：开书第一卷和写作中拆卷都能渲染，`reveals`、`new_expectations` 都能保存。
10. **提示词**：提示词页能看到两个新模板；变量校验通过；`default_changed` 的判断正确。
